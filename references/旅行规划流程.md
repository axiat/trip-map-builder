# 旅行规划流程（5 步，可复用）

> 每次规划出行按此流程走。Part 1 的结论沉淀在画像文件（按人拆分 `画像_<人>.md`，索引 `旅行者画像.md`），跨次复用；
> Part 2-5 的产物进当次出行文件夹 `Travel/YYYY_<事件>/`。

开始前选一次模式：**自动走完**或**交互式**。未指定时先询问，选定后按本次模式执行。
自动走完模式由 AI 根据画像、约束和调研完成方向、行程与餐饮取舍，连续生成交付物；
只有缺少会改变目的地或日期的硬约束、关键地点无法核实时才集中提问。
交互式模式按各阶段的确认点与用户讨论。两种模式都保留事实核查、取舍依据和归档。

## Part 1 用户画像（先沟通，再决定）

- 先读 `旅行者画像.md`；有新的出行人先补画像，有画像的核对是否有变化。
- 已有画像和本次说明足以支持决策时直接使用；缺少关键偏好时集中提问。跨次稳定的新增偏好写回画像文件，以后不再重问。
- 画像只写跨次稳定的个人信息；与当次目的地/行程绑定的判断（如"本次候选目的地海拔低"）进当次出行文件夹，不写进画像。
- 每个画像文件维护五节（对照查漏）：
  - **基本属性**：年龄/居住、体能与日徒步上限、交通（可否自驾/长途耐受）、预算量级、住宿底线、日程刚性、饮食禁忌与硬约束（不会游泳等）
  - **关系**：与我的关系（影响同行决策权重）
  - **偏好**：景观、天气敏感（怕热/怕冷/雨雾容忍/能见度）、拥挤容忍（排队耐心，"人少"是绝对还是相对）、活动类型（徒步/表演/人文/科技装置…）
  - **去过的地方**：正样本（喜欢、常提起）+ 负样本（踩雷、无感），避免重复推荐
  - **原始 fact**：重要行程的原始记录（细节以这里为准）

## Part 2 情境与方向

分三步。交互式模式在方向收敛后与用户对齐；自动走完模式依据画像和调研自行收敛，
只对收敛后的方向深挖，避免把调研成本花在会被排除的方向上：

### 2.1 宏观扫描（AI 轻调研，一页结论）

- 本次假期的时间特征：放假结构、能否错峰、全国客流大盘与高峰日
- 全国天气格局：哪些区域晴好、哪些区域阴雨（结合画像里的天气敏感项）
- 当季景观时点：想看的景观类型是否正当季
- 产出：一页宏观结论直接给用户看；**此阶段不选目的地**

### 2.2 大方向收敛

- AI 基于画像 + 2.1 宏观，提 3-5 个**大方向**（区域×玩法×预算量级，如"京郊轻量 / 北方冷门秋色 / 正样本复访"），不是具体行程
- 交互式由用户（和同行人）讨论后收敛到 1-2 个方向；自动走完由 AI 依据画像和宏观结论收敛，并记录理由
- 此步不派 subagent 深挖，靠已有知识 + 轻量搜索即可

### 2.3 定向深挖（AI 重调研）

- 只对收敛后的方向做深度实时调研：天气窗口、票务与稀缺资源、拥挤度、预算
- 多目的地对比时派并行 subagent，事实带来源 URL；查不到的实时库存列"需用户自查"清单
- 产出：候选对比表，沉淀进当次出行 README

## Part 3 思路发散

- 在 2.2 收敛出的方向上，生成若干**差异拉开**的思路（不是单一目的地微调），每个思路给具体方案：交通、行程骨架、预算、风险。
- 思路示例维度：零摩擦本地 / 冷门替代 / 反向错峰 / 大景区错峰打法（早进晚出避开排队）。
- 每个思路明确标注它满足了画像里的哪些点、牺牲了哪些点。

## Part 4 共同决策

- 交互式由用户拍板思路；自动走完由 AI 依据约束和调研选择思路。随后细化成可执行清单：订票（具体班次）、预约（渠道+放票时间）、住宿、天气复查节点。
- 决策理由记一句进当次 README（为什么选它、放弃了什么），供以后 Part 1 参考。
- **细化排程方法以 skill 为准**：拍板后进入 trip-map-builder skill 的三阶段流水线（硬约束抽取 → 删高风险点 → 按区域排程 → 大众点评/小红书选餐）。该 skill 已对接本画像体系（读 `画像_<人>.md`，多人约束求交），画像已覆盖的信息直接生效。
  - 硬约束抽取、删点原则（主动删、明说删了什么和为什么）、选餐原则（餐厅是补给点不是锚点，点评+小红书双源）均以 skill 的 `references/trip-planning.md` 为准。
  - 交互式模式在砍点方案、行程骨架、餐饮候选处与用户对齐；自动走完模式记录取舍并继续。

## Part 5 交付讨论

行程定稿后，交付物固定为**一幅手绘图 + 一张行程表 + 一个交互式地图页面**，数据同源（同一份逐日结构化数据），归档进当次出行文件夹。交互式模式先与用户确认交付内容：

- **手绘旅行地图**（1 张图）：用下方固化的生成 prompt，填入当次旅行资料后生成。生成前先核对地理位置，无法核实的关键地点先向用户要地图截图或定位。
- **行程总表**（1 张表）：按天排列，覆盖住宿 + 景点 + 重要餐食时间线 + 预期价格，作为执行和预算核对的依据。
- **交互式地图页面**（1 个 HTML）：由 trip-map-builder skill 基于 `assets/template.html` 生成，旅途中查位置、跳转导航/小红书/大众点评用；可选部署到 Vercel，部署地址记进当次 README。

### 手绘旅行地图 · 固化生成 prompt

每次使用时填写【旅行资料】部分，其余规则原样保留：

````text
请根据以下旅行资料，生成一张以真实地理位置为基础的可爱手绘旅行地图。画面兼顾景物插画、路线识别和简洁的行程查阅。

【旅行资料｜每次填写】

目的地：
旅行日期：填写年份、月份和日期。
逐日行程：
第1天：日期｜景点顺序｜住宿地点｜可选项目
第2天：
……按实际天数填写，也可直接粘贴完整攻略。

出发地、同行描述：可留空，用于副标题。
参考资料：可留空，可附地图链接、地图截图、景点定位或参考画风。
特别要求：可留空，例如必须保留的景点、需要上图的交通时刻、路线配色。

【一、地理位置】

先查阅可靠地图或使用所附地图，核对景点、市区、机场、车站和住宿地点的位置，再安排画面。

地图默认上北下南。各地点的相对方位、远近关系和交通连接应有地图依据。先确定地点位置，再绘制景物插画；景点图标可以适度放大，必要时用短引线连接实际位置。

相距较远的地点之间允许留白，也可少量绘制当地真实的山林、平原或水域。保持实际空间关系优先于填满画面。

景点密集时可以增加单独的局部放大图，并注明放大区域。河流走向、湖泊位置和道路连接依地图绘制。游览路线与实际道路采用不同画法。

同一地点只绘制一次。多天经过或游览同一地点时，在该地点标注多个日期。

角落小字注明"旅行示意图"。指北针与实际方向一致；只有采用统一比例时才绘制比例尺。

若关键地点无法核实，先请求补充地图截图或定位，再生成图片。

【二、画风】

固定为3:4竖版。

采用可爱的蜡笔／彩铅手绘风格，奶白色纸张质感底，线条圆润，保留细腻的颗粒笔触。色彩清新明快，主色根据当地景观和旅行季节选择。

山林、建筑、湖泊、动物和食物绘制成容易辨认的微缩插画。建筑和自然景观保留主要外形特征。

季节和节日元素少量融入景物，例如秋叶、积雪或月亮。具体天气和气温仅使用已确认的信息。

全图使用简体中文。标题有手写感，地名、日期和行程文字清晰可读，适合手机查看和打印。

【三、版式】

顶部：
大标题采用"目的地＋旅行主题"；未提供主题时使用"目的地旅行地图"。
副标题写日期、出发地及已提供的同行描述，缺失字段直接省略。

主体地图：
占画面约三分之二，是全图的主要内容。
景点直接绘制在对应位置，旁边标注地名。住宿地点使用小房屋或床铺图标，注明入住日期。
每日路线用虚线和小箭头连接，方向与实际行程一致。
默认按天分色；若特别要求统一颜色，则全程使用棕色路线。
日期使用简洁的小纸签，例如"9/24"，贴近当天路线起点。地图布局按地理位置组织，日期标签负责区分每天的活动。
可选景点标注"可选"，与确定行程区分。

特色插画带：
位于地图下方，保留3—4个有资料依据的当地美食小插画，仅标名称。
必要的小贴士最多3项，用图标＋短词表达，例如"保暖衣物、雨衣、登山杖"。
未提供且无法核实的内容直接省略。

底部行程概览：
按实际天数排列简洁小格。
每格仅保留日期、一行主要活动、一行住宿或返程信息。
例如：
9/24
抵达 · 市区散步
宿：市区

地图已列出的完整景点清单不再重复抄入概览。

【四、信息密度】

文字限于标题、日期、地名、路线、住宿、必要交通信息和少量实用提示。

不增加抒情口号、宣传语、装饰性段落或重复的"必打卡"清单。节日彩蛋和小装饰以图形呈现。

景点之间保留明显空白，文字与图标之间保持间距。内容较多时优先缩减说明文字和重复信息，保证地名与日期的字号。

【五、生成前检查】

核对地点相对位置、路线箭头方向、日期对应、住宿日期和中文地名。
地图与底部概览保持一致。
确认行程与可选项目分别标示。
所有上图信息均来自旅行资料或已核实的来源。

资料充分时直接绘制；仅在关键地理位置或行程存在无法解决的歧义时提问。
````
